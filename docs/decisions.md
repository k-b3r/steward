# Decisions

A dated, numbered log. One entry per decision. `UNVERIFIED:` marks a claim this repo has not
tested. Open items come last. Do not renumber entries.

## 2026-10-27

### 1. Flat repository layout

Fit check in `CONTEXT.md`: one feature area, fewer than three data-owning features. Pure
decision code sits in files beside the shell code, not in modules. Split into modules when a
phase adds a feature with its own data (validation reports, pull request records).

### 2. One instance per context

`INSTANCE` names the context (`personal`, later `work`). It prefixes every external name:
systemd units, Quadlet containers and services, Podman network and volumes, secrets, ports,
database, env file, and the instance folder. Nothing is a global singleton. A second instance
needs only a second instance folder and a second render, not a code change.

### 3. Postgres is the source of truth

Postgres holds jobs, job events, slots, and pending actions. BullMQ carries job ids only and
runs delayed jobs. The worker re-reads the job from Postgres before acting. Retry policy
lives in `src/retry-policy.ts`, not in BullMQ. A startup reconciler requeues `queued` jobs
missing from Redis, fails `running` jobs with no live worker (kind `infra`), and frees slots
held by final or failed jobs.

### 4. Slots are held only in `claiming` and `running`

The first brief held a slot until the job was final. That would let open drafts occupy every
slot while a person reviews them. `HOLDING_STATES` in `src/allocate.ts` is `claiming` and
`running` only. A job waiting for review holds no slot. `findLeakedSlots` reports slots held
by jobs in any other state, and the reconciler frees them.

### 5. Failure kinds are `infra`, `agent`, `setup`

One kind string and a free-text reason on the job event. `infra` retries with exponential
backoff until `maxAttempts` (default 3). `agent` goes to the phase 3 validation loop.
`setup` is never retried. `failed` means retries are exhausted and is the dead-letter state.

### 6. Baseline rule for tickets already `In Progress`

Tickets already `In Progress` on the first poll for a source become `proposed`, not run. The
same applies when a poll returns more than `MAX_ENQUEUE_PER_POLL` items, and when open
proposals reach `MAX_OPEN_PROPOSALS`. This stops the first poll from starting a burst of
work. A person confirms each proposal.

### 7. A draft pull request is the visible claim

Phase 4 claim: the orchestrator pushes an empty commit to the job branch (the ticket id, see
decision 29) and opens a
draft PR, before the agent starts. The PR is the lock a person can see. If validation fails,
nothing is pushed and the draft stays empty. `UNVERIFIED:` GitHub's acceptance of a
pull request from an empty commit is not tested yet; see open items.

### 8. Hono with a typed RPC contract

The API uses Hono, a `/v1` prefix, chained routes, and `src/api/contract.ts` exporting
`AppType` plus zod schemas. The future dashboard imports only those types, enforced by
dependency-cruiser. Nothing in the dashboard imports server code.

### 9. Transcript plus raw file

`transcript.jsonl` holds one envelope per line, `{ seq, ts, kind, data }`, with monotonic
`seq` for SSE resume. `raw.jsonl` holds the byte-exact runner output. Both are mode 0600 in
a 0700 directory. Redaction applies to orchestrator lines and process logs, not to agent
output. The API never serves `raw.jsonl`.

### 10. No labels on tickets

The tracker filter is team key, assignee, and status (`Todo`, `Backlog`, `In Progress`). The
orchestrator does not require or add labels, so a ticket needs no setup beyond assignment.

### 11. Personal instance first

Build and test against a personal workspace and a private scratch repo. Every phase starts in
dry-run. The work instance is a second config and env file on the same box, created only
after the personal instance completes a full ticket-to-draft-PR cycle. The two instances do
not share databases, Redis, network, ports, or runs directory.

### 12. Deploy target: Podman 4.9.3 rootless, systemd user units

Verified on this box: `podman --version` reports 4.9.3, `podman info` reports rootless mode
with cgroups v2 and the systemd cgroup manager. `systemd-analyze --version` reports systemd 255. Postgres, the queue Redis, and the slots Redis are rootless Podman containers started
from Quadlet files. The API and the worker run on the host as systemd user units, not in
containers. A dedicated `steward` system user is a documented option, not the default: the
default is the login user's own user units with linger enabled.

### 13. Unit and container names

The two host units are `steward-api@<instance>.service` and
`steward-worker@<instance>.service`, so a role can restart without the other. The Quadlet
files render to `steward-<instance>-postgres`, `-redis-queue`, `-redis-slots`, and
`steward-<instance>.network`, with the usual `.service` names generated by Quadlet. Volumes
are `steward-<instance>-pgdata` and `steward-<instance>-redis-queue-data`. `instanceNames()`
returns `steward@<instance>` as the instance unit prefix; the deployed units insert the role
before the `@`. No code uses the unit name today.

### 14. Ports are published on `127.0.0.1` only

One port base per instance. Postgres uses the base, queue Redis uses base+1, slots Redis uses
base+2, all bound to `127.0.0.1`. The API port comes from `API_PORT` (default 3000); the API
must bind `127.0.0.1` itself. Nothing listens on the LAN. The render script validates the
base in 1024..65530, so base+2 never exceeds 65532.

### 15. Database passwords come from Podman secrets

Both containers get their password from a Podman secret of type `env`:

- `Secret=steward-<instance>-postgres-password,type=env,target=POSTGRES_PASSWORD`
- `Secret=steward-<instance>-redis-password,type=env,target=REDIS_PASSWORD`

The secret value is not in the Quadlet file, the repo, or the systemd unit. The alternative, a
container `EnvironmentFile=` pointing outside the repo, would also keep the value out of the
repo, but it puts the password in a plain file that systemd reads. The Podman secret is the
supported route on this version and keeps the value in Podman's secret store. The operator
creates each secret once with `podman secret create`, as the README describes. The app reads
the same passwords from its env file, because it connects over TCP. Podman 4.9 supports
`type=env` for `--secret` and `Secret=`; the Quadlet generator emits it in the generated
`podman run` line (verified, entry 21).

### 16. Redis requires a password without a secret in the unit file

`redis-server` takes `--requirepass`, and the official image has no environment variable for
it. The unit runs `sh -c` inside the container and reads the password from the secret-backed
`REDIS_PASSWORD` variable:

```
Exec=/bin/sh -c "exec redis-server --requirepass \"$$REDIS_PASSWORD\" --appendonly yes"
```

`$$` is the systemd escape for a literal `$`, so systemd passes `$REDIS_PASSWORD` to the
container shell instead of expanding it to an empty string. The generated unit keeps `$$`
(verified, entry 21). Limitation: the password is in the `redis-server` process argument list
inside that container. It never appears in the repo or in the unit file.
`UNVERIFIED:` the runtime expansion and Redis startup were not executed, because this task
runs no containers.

### 17. Quadlet keys used

The files use these keys: `[Container]` with `Image`, `ContainerName`, `Network`,
`PublishPort`, `Volume`, `Environment`, `Secret`, `Exec`; `[Service]` with `Restart=always`
and `TimeoutStartSec`; `[Network]` with `NetworkName`; `[Volume]` with `VolumeName`; `[Unit]`
with `Description`; and `[Install]` with `WantedBy=default.target`. All of them are listed in
`podman-systemd.unit(5)` on this box (Podman 4.9.3), and the generator accepted every file
(entry 21). `WantedBy=default.target` is the supported user-unit target. `TimeoutStartSec=900`
allows the first image pull.

### 18. Pin the network and volume names

Quadlet would name the network `systemd-steward-<instance>` and the volumes
`systemd-steward-<instance>-*`. That would not match `instanceNames().redisNetwork` and would
be awkward to type. `NetworkName=steward-<instance>-net` and explicit `VolumeName=` values
make the real Podman names predictable and match the code. Containers reference the network
by its Quadlet file name (`Network=steward-<instance>.network`), so Quadlet adds the
dependency.

### 19. A volume for the queue Redis

The brief lists a volume for Postgres only. `appendonly yes` without a volume is pointless:
Quadlet runs the container with `--rm`, so the AOF file would disappear on every restart.
`steward-<instance>-redis-queue-data` holds `/data`. The slots Redis has no volume, because
its data is disposable by design.

### 20. `@PG_DB@` matches `instanceNames().dbName`

The Postgres database name is `steward_<instance>` with hyphens replaced by underscores, the
same rule as `instanceNames().dbName`. The render script computes it and substitutes
`@PG_DB@`, so an instance named `work-demo` gets `steward_work_demo` in the container and in
`DATABASE_URL`. A hyphen in an unquoted database URL would be ambiguous, and Postgres folds
unquoted identifiers.

### 21. Verified with the Quadlet generator

Method: rendered the templates with `deploy/render.sh personal 15432 <tmpdir>`, then ran
`QUADLET_UNIT_DIRS=<tmpdir> /usr/lib/systemd/system-generators/podman-system-generator --user
--dryrun`. Exit code 0, no warning lines, and six services were generated:

- `steward-personal-postgres-volume.service` → `podman volume create --ignore steward-personal-pgdata`
- `steward-personal-redis-queue-volume.service` → `podman volume create --ignore steward-personal-redis-queue-data`
- `steward-personal-network.service` → `podman network create --ignore steward-personal-net`
- `steward-personal-postgres.service` → `--publish 127.0.0.1:15432:5432 --secret ...`
- `steward-personal-redis-queue.service` → `--publish 127.0.0.1:15433:6379`, Exec keeps `$$REDIS_PASSWORD`
- `steward-personal-redis-slots.service` → `--publish 127.0.0.1:15434:6379`, `--appendonly no --save ''`

Each container service has `Requires=`/`After=` for its network and volume services, and
each generated `podman run` line has the expected image, volume, secret, and publish flag.

### 22. The render script

`deploy/render.sh <instance> <port-base> <output-dir> [--force]` validates the instance with
the config regex and the port base as an integer in 1024..65530, computes the three ports
and the database name, and writes only into `<output-dir>`. It checks every destination
before writing any file, so a refused run changes nothing. It refuses to overwrite without
`--force`. `deploy/render.test.sh` renders into a temporary directory and checks the file
set, leftover placeholders, the three `127.0.0.1` bindings, secret names, persistence flags,
the overwrite guard, hyphen handling, and rejected inputs. Ran with `bash
deploy/render.test.sh`: 46 checks, 0 failures.

### 23. Host unit hardening and paths

Both units set `NoNewPrivileges=yes`, `ProtectSystem=strict`, `PrivateTmp=yes`, and
`Restart=on-failure`. `WorkingDirectory=%h/steward` points at the app checkout, not at instance
data; edit the unit when the app is cloned elsewhere. `ExecStart=/usr/bin/node
dist/entries/api.js` and `ExecStart=/usr/bin/node dist/entries/worker.js`.
`EnvironmentFile=%h/steward-instances/%i/.env` is the instance's env file. The worker alone
gets `ReadWritePaths=%h/steward-instances/%i`, the whole instance folder: it writes
transcripts and worktrees under `runs/`, and `git worktree add` writes into the clone's `.git`
under `repo/`. `RUNS_DIR` defaults to `$HOME/steward-instances/$INSTANCE/runs`. That directory
must exist before the unit starts, so the README creates it: systemd requires a
`ReadWritePaths=` path to exist while the directive is enforced. The API only reads. With
`ProtectSystem=strict`, any other write path must be added explicitly. On this box the
directives are not enforced for user units (see "User units do not sandbox..." below); they
are correct for system units.

### 24. Template unit dependencies use `%i`

`Requires=`/`After=` name `steward-%i-postgres.service` and the two Redis services. With no
instance, `systemd-analyze --user verify deploy/systemd/steward-api@.service` reports the
dependency names as missing units, which is expected for a template. Verified on copies with
`%i` replaced by `personal`, together with the generated container services:
`systemd-analyze --user verify` exited 0 with no output. A deliberately broken unit in the
same directory was reported as an error, so the check was live.

### 25. Build output path is `dist/`

The units expect `dist/entries/api.js` and `dist/entries/worker.js`. `tsconfig.json` sets
`noEmit`, and `package.json` has no build script. This is open item 1. Do not add a build
script as part of deploy work; decide the compiler (tsc or a bundler) with the phase 1 code.

## Where steward keeps its repos and runs (2026-10-28)

Revised 2026-10-29: the single `~/steward` root is replaced by one folder per instance. See
"Two roots: app and instance data" below.

- One folder per instance, `~/steward-instances/<instance>/`, named like `INSTANCE`. It holds
  `.env`, `repo/`, `runs/`, `quadlet/` and `backups/`.
- The clone lives at `repo/` inside it (`REPO_PATH`), one clone per instance: identity and
  credentials are per clone, so the personal and work instances never share a commit author
  and no `gh auth switch` is needed at run time.
- Runs live under `runs/<jobId>/` (`RUNS_DIR`): the worktree, `transcript.jsonl` and
  `raw.jsonl`.
- The env file is `.env` in the same folder, mode 0600, and the folder is 0700.
- One folder per instance, so "this is steward's data" is visible, cleanup is one directory,
  and adding or removing an instance is adding or removing one folder. Adding a repo is
  filling that instance's `repo/`; removing it is deleting the folder.
- Each clone is marked as steward's, in local git config (`steward.instance`, `steward.role`,
  `steward.repo`) and in `.git/steward.json`. Neither is committed, both survive a move, and
  `git status` stays clean.
- `scripts/setup-repo.sh` (alias `pnpm repo:setup`) clones and marks; it is idempotent and
  prints the `REPO_PATH` line for the env file.

## Two roots: app and instance data (2026-10-29)

Two roots, not one: the app checkout, and `~/steward-instances/<instance>/` per instance.

```
~/steward-instances/<instance>/
  .env      secrets, mode 0600; the folder is 0700
  repo/     the clone (REPO_PATH)
  runs/     job output (RUNS_DIR default $HOME/steward-instances/$INSTANCE/runs)
  quadlet/  the real rendered Quadlet files
  backups/  podman volume export files
```

**Why.** Everything an instance owns is state about one repo and shares one lifecycle: you add
a repo, you remove a repo, and the folder follows. One folder per instance, named like
`INSTANCE`, makes that visible: everything the instance owns is in it, and deleting an
instance deletes one folder. The app checkout is separate and unchanged: it is code with no
instance state, and the units' `WorkingDirectory=` points at it, never at instance data.
`~/.config/containers/systemd` holds symlinks to the files in `quadlet/`, so the real files
live with the instance data and one removal takes them too.

**What stays outside, and why.**

- The Postgres volume stays in Podman's store, not in the folder. Its files are owned by a
  sub-uid and are not readable as the user, so `podman volume export` into `backups/` is the
  only usable copy.
- Two tool-owned folders stay outside: `~/.config/containers/systemd` (Quadlet) and
  `~/.config/systemd/user` (systemd units). The Quadlet folder holds symlinks to the files in
  the instance's `quadlet/`. The unit folder holds copies, as the README installs them, or
  symlinks made with `systemctl --user link`, which was tested with a unit living elsewhere.
  Neither holds state worth backing up: a copy or a link is recreated from the app checkout
  or the instance folder.

**Verified facts.**

- (a) Quadlet follows symlinks. Six symlinks in `~/.config/containers/systemd` pointing at
  files elsewhere produced the same six services as the real files; only the process ids
  differed. Tested with podman 4.9.3:
  `QUADLET_UNIT_DIRS=<dir> /usr/lib/systemd/system-generators/podman-system-generator --user --dryrun`.
- (b) `systemctl --user link <unit>` registers a unit that lives elsewhere. Tested, and the
  probe unit was removed.
- (c) The agent-config guard (`hooks/guard.mjs`) blocks reads of files named `.env` or
  `.env.*` only. A file named `<instance>.env` was **not** protected, so the file is named
  `.env`. In a pi session no guard hook was found, so open agent sessions in `repo/` or
  `runs/`, never in the instance folder.
- (d) This machine has no backup, sync or dotfiles tool, so the leak risk is agent reads, not
  a sync client copying the file somewhere.

**Per-job lifecycle.** The worktree `runs/<job-id>/worktree` is created at claim and removed
in `finally` after every outcome (done, failure, cancel). `transcript.jsonl` and `raw.jsonl`
stay. The job branch (decision 29) stays in `repo/`, so a retry or a later run continues it. The
retention sweep and branch cleanup are phase 5 and are not built.

**Known bug (not fixed here).** If the worker dies mid-run, `finally` never runs. The worktree
path stays registered, and the next attempt's `git worktree add` fails with `already exists`
(`git.test.ts` pins that error), so the job can never recover without manual cleanup. Planned
fix: call `removeWorktree` on the path before creating the worktree, test first, in its own
PR. Note that `removeWorktree` uses `--force`, so uncommitted work in a stale worktree is lost.

## Which account an instance acts as (2026-10-28)

- Per instance, in the env file (`~/steward-instances/<instance>/.env`), non-secret: `GH_ACCOUNT`, `GIT_USER_NAME`, `GIT_USER_EMAIL`. Validated by `config.ts`; they are not redacted, because a mismatch is exactly what you want to see in a log.
  - Each instance has its own values, so an instance can only ever act as its own account. The real values live in each instance's env file, outside the repo; `.env.example` shows the shape with placeholders.
- No token in config. At push time the worker runs `GH_TOKEN=$(gh auth token --user "$GH_ACCOUNT")`. If the service user cannot use `gh`, one secret `STEWARD_GH_TOKEN` in the same env file; nothing else carries credentials.
- The identity is config, not clone state, because **the agent commits inside the container**, which has no `~/.gitconfig`. The container gets `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL` from these values (phase 2).
- `scripts/setup-repo.sh` reads them from the env file, clones with that account's token, and sets the clone's local `user.name`, `user.email` and `steward.account`, so the clone cannot disagree with the instance.
- The phase 4 pre-push check refuses to push unless the clone's `steward.instance` equals `INSTANCE`, the clone's `user.email` equals `GIT_USER_EMAIL`, and `gh api user` for the resolved token returns `GH_ACCOUNT`. Failure kind `setup`, never retried.

## User units do not sandbox the filesystem on this box (2026-10-28)

Checked on Ubuntu 24.04, systemd 255, with `systemd-run --user` and a probe command:

| Directive               | Effect in a user unit here                            |
| ----------------------- | ----------------------------------------------------- |
| `NoNewPrivileges=yes`   | **Applied** (`NoNewPrivs: 1`)                         |
| `PrivateTmp=yes`        | **Not applied**: a file in the host `/tmp` is visible |
| `ProtectHome=read-only` | **Not applied**: a write to `$HOME` succeeds          |
| `ProtectSystem=strict`  | **Not applied**: a write to `$HOME` succeeds          |

Cause: those three need a mount namespace, which a user manager builds inside an unprivileged user namespace, and Ubuntu 24.04 denies that (`kernel.apparmor_restrict_unprivileged_userns=1`; a manual `unshare -Ur` also fails). systemd does not report an error; the units start as if the sandbox were there.

Consequences:

- The orchestrator process (API and worker) runs **unsandboxed** as the login user. Do not rely on `ProtectSystem` or `PrivateTmp` for it; `ReadWritePaths=` is not enforced either, and a missing path does not stop the unit, so the earlier note that "the unit fails to start when the path does not exist" does not hold in user mode.
- The directives stay in the units, because they are correct and take effect if the services run as system units under a dedicated user.
- The real isolation boundary is the one planned for phase 2: the Podman container the agent runs in, which has its own mount, user and network namespaces, no credentials, and only the worktree mounted. The orchestrator is the trusted side, and it holds the tokens.
- Open item: decide whether the orchestrator should run as a system unit under a dedicated `steward` user (sandbox enforced), or stay a user unit and accept the above.

## Decisions taken 2026-10-28

- **A fetch failure is `infra`, unless the setup is wrong.** A missing remote, a missing base branch, or `Repository not found` fails the job as `setup` at once, because retrying cannot fix it. GitHub answers a wrong URL and a token without access with the same `Repository not found` text, so both land here: each needs the owner to act, and an early `failed` with that reason beats waiting through the backoff. Everything else raised by the fetch (network, timeout, and the other auth messages such as `Authentication failed`) is `infra` and retried with backoff. That leaves auth errors split by message wording, which is accepted for now. Classification happens at the fetch call only, so the same words from anywhere else in a job stay `infra`.
- **The personal instance runs on its Quadlet stack**, not the disposable test containers: `steward-personal-postgres` and the two Redis servers, so data survives restarts.
- **`BASE_BRANCH` is per instance.** A new job branch is cut from `origin/<BASE_BRANCH>`; default `main`.
- **`DASHBOARD_DIR` serves the built dashboard from the API's origin** when set. One origin, no CORS, and the CSP's `connect-src 'self'` holds. Unset means the API answers only `/v1`.
  - The static route is `app.get('*')` in `src/composition/api.ts`, added after `createApp`, so it sits outside `/v1/*` and **skips both the Host check and the bearer auth** (`src/api/app.ts` mounts `createAuthMiddleware` on `/v1/*` only). That is fine for public built assets, but it means **nothing secret may ever be placed in `DASHBOARD_DIR`**: anything readable by the API user can be fetched by anyone who can reach the API port, including over a tailnet.
  - Accepted limitation: `resolveAssetPath` normalises the joined path and rejects `..` and absolute paths, but it does **not** resolve symlinks (`src/platform/static.ts` calls `normalize`, not `realpath`). A symlink inside `DASHBOARD_DIR` can therefore point outside it and be served. Low risk, because `DASHBOARD_DIR` is operator-controlled and the operator is the one creating the symlink.
- **The orchestrator never moves a ticket past `In Progress`.** `ALLOWED_STATUSES` defaults to `[In Progress]`, so the only tracker status change it may make is Backlog or Todo to In Progress, as part of a confirm. Everything after that is yours.
  - That limit is only enforced once phase 4 builds the confirm path. **Today intake only reads tickets, and nothing in the code writes to Linear**: no status is moved at all, so the guarantee currently holds by absence, not by a check.
  - `ALLOWED_STATUSES` is parsed and validated but **not read by anything outside config**: `grep -rn ALLOWED_STATUSES src` returns `src/platform/config.ts` (the type field, the `parseStatuses` preprocess that splits on commas and defaults to `['In Progress']`, and the schema's `.min(1)` that rejects an empty list) and `src/platform/config.test.ts` only. Wired: config loading, defaulting, validation and redaction. Not wired: intake, the confirm command, and the Linear client, which take no status argument. Phase 4 must pass `ALLOWED_STATUSES` to the write path and check the target status against it before any mutation.
- **The build is undecided.** There is no build script yet. `tsconfig.json` uses
  `moduleResolution: Bundler`, and `src/` has about 129 relative imports without a `.js`
  extension, which Node cannot load from plain `tsc` output. Two options, neither chosen: add
  `.js` to every relative import, or emit with esbuild (`--packages=external`) and copy the
  migrations next to the output.
- **The systemd units stay user units**, and the phase 2 container is the isolation boundary, since the filesystem sandbox is not enforced for user units on this box.
- **ntfy is self-hosted**, and carries the identifier and title only, never ticket bodies (phase 4).

## Worktree and branch rule (2026-10-28)

How a job gets the code it works on. Decided for phase 2; the git primitives land now.

- The orchestrator never clones per job. `REPO_PATH` is one clone on the host, per instance, and each job gets a **git worktree** cut from it (`<runsDir>/<jobId>/worktree`). A worktree shares the clone's objects, so six slots cost kilobytes, not six copies of history, and the container needs no git credentials at all.
- Before cutting, every run runs `git fetch --prune origin <base>` and starts from `origin/<base>`, never from the clone's `HEAD`. `HEAD` may be stale or checked out on some other branch, which was a real bug until this change.
- **No pull request yet:** create the job branch (decision 29) from `origin/<base>`.
- **A pull request already exists:** attach the **existing PR head branch** into the worktree and **merge `origin/<base>` into it**, so the agent continues the same PR instead of opening a second one. Merge, never rebase: a rebase would rewrite the PR branch and need a force-push.
- **A conflict is for the agent to resolve.** `mergeIntoWorktree` returns `'conflict'` and leaves the markers in the worktree, because resolving a merge is coding work. Phase 2 hands that tree to the runner. **Not built yet:** the runner handoff, and a guard that fails the job as `agent` when the same job conflicts a second time or the `origin/<base>..branch` diff is large (`abortMerge` exists for that path and is only exercised by its own test). Until then the phase 1 stub has no agent to give the tree to, so it fails the job as `agent` with the reason `merge conflict with origin/<base>`, leaves the branch as it was, and removes the worktree. A job that reports `done` after discarding a conflict would be wrong.
- `jobs.branch` will store the branch actually used, set at claim time (phase 4). It is never recomputed from the identifier afterwards, because a PR's head branch can differ (Linear suggests `branchName`, which is a suggestion, not the PR branch). Phase 1/2 use the rule "attach if the branch exists, else create from the base".
- The agent commits locally in the worktree. The orchestrator pushes, opens the PR and updates the tracker, from the host, with the instance's git identity checked first.
- A failed fetch is classified at the fetch call. A permanent cause (no such remote, a missing base branch, `Repository not found`) fails as `setup` at once. A transient one (a network blip, a timeout) is `infra`: retried with backoff up to `MAX_ATTEMPTS`, then it lands in `failed`, the dead-letter, where you retry or cancel it.
- Cleanup: the worktree is removed after the run; the branch stays (retries reuse it). Phase 5 deletes merged job branches (by the branch recorded for each job, since the name no longer has a prefix to match) and prunes dead worktrees.

## Decisions taken 2026-11-07

### 26. A `ci_failed` state between `pr_open` and `in_review`

A pull request whose checks fail is neither waiting for review nor finished, and it must keep its
ticket blocked. It gets its own state instead of reusing `failed`, because `failed` means retries
are exhausted and offers a retry, while here the right move is to resume the agent.

- Edges: `pr_open -> ci_failed` and `in_review -> ci_failed` (a check failed on this PR),
  `ci_failed -> running` (the agent is resumed), `ci_failed -> in_review` (a person fixed it),
  `ci_failed -> failed | cancelled` (as its neighbours).
- "Ongoing" means CI is red because of this PR. A failure that also occurs on `BASE_BRANCH` does not
  count.
- It holds no slot, like `pr_open`: waiting for a fix must not starve the worker.
- A person can cancel it, and cannot retry it: it is not stopped, it is ongoing.
- Landed now: the state, its edges, the database constraint (migration `0001`), the API contract and
  the dashboard label, icon and lane. The dashboard borrows the `failed` colour and icon, as it
  does for other states the design has none for.
- Not landed, undecided: which check results move a job here (GitHub's checks, or a validation
  verdict from phase 3). The base-branch comparison needs the phase 5 poller, so the classification
  lands then. Nothing in the code sets this state today.

### 27. Runs are their own table, and transcripts are kept per run

`jobs` stays one row per ticket (`source + externalId` is unique) and ends at `merged`. Each
execution gets a row in `runs` (migration `0002`), so a ticket's history of attempts is data, not
something to read out of `job_events`.

- A run opens and closes inside `transitionJob`, in the same transaction as the state change. The
  rule is the slot rule: entering `claiming` or `running` from a state that holds no slot opens a
  run, leaving them closes it (`src/runs.ts`, with a test that every legal way out of a slot-holding
  state has an outcome).
- A manual `retry` from `failed` is a new run. The `attempt` counter resets, the run number does not.
- `merged` does not close a run and needs no sweep: the last run already ended when the job
  left the slot.
- Transcripts move to `runs/<job-id>/<run-number>/`. Before this, a second run appended to the same
  `transcript.jsonl`, and the two could not be told apart. `seq` now restarts at 1 in each run, so
  a log stream stays on the run it opened on instead of following a newer one.
- `AgentRunner.start` takes the run number. `cancel` and `resume` act on the newest run's folder, and
  `cancel` no longer creates a folder for a job that never ran.
- Not migrated: jobs that ran before this have no `runs` rows and keep a flat transcript folder. The
  API reads that folder when a job has no runs, so old logs stay visible. Nothing backfills them.
- Read side only: a job's runs show in the API (`/runs`, `?run=`) and the dashboard lists them,
  pinning the one whose transcript is on screen. The job page also shows the state log (`/events`)
  as a timeline. Nothing is written to Linear.

### 28. A lost database connection is logged, never fatal

`createPool` registers an `error` listener (`src/platform/db.ts`), so an idle client that loses its
server reports the message instead of raising an unhandled event, which Node turns into a crashed
process. Before this, restarting Postgres killed the worker, and the API on its next query. The
listener is registered even when the caller passes no handler, so a new caller cannot reintroduce
the crash.

### 29. A job branch is the ticket identifier, as is

The branch a job works on is its ticket identifier exactly as the tracker gives it: `INV-12`, not
`agent/inv-12`. No prefix, no lowercasing. `branchName` in `src/branch-name.ts` is the one place
that decides it: it replaces a character git refuses in a branch name with `-`, drops a leading
`-` (git would read the branch name as an option), and throws when nothing usable is left. Amends
decision 7 and the worktree rule.

- **Why:** a branch should not name an "agent" author, and the ticket id is what a person and the
  tracker already search for.
- **Cleanup changes.** Phase 5 can no longer delete `agent/*`. It must delete only the branches
  recorded for steward's own jobs, so a branch you made by hand is never touched.
- **A branch named for the ticket may already exist**, made by you or by Linear's copy-branch
  button. The existing-branch rule applies: steward attaches it and merges the base into it.
  Steward can then commit to a branch you were using.
- **Existing branches named `agent/*`** from earlier runs are not renamed. A retry of such a job
  starts a new branch named for the ticket.
- Case matters to git: `INV-12` and `inv-12` are two branches.

## Decisions taken 2026-11-08

### 30. Pi's JSON stream is mapped by a pure function, not by the runner

`src/runner/pi-events.ts` reads `pi --mode json` output (Pi 1.5.0, `docs/json.md`). It starts no
process, reads no clock and does no I/O, so the mapping is tested from fixtures and the runner
that follows only wires a pipe to it.

- `createPiLineSplitter()` splits on LF only and strips one preceding CR. Node's `readline` also
  splits on U+2028 and U+2029, which are legal inside a JSON string, so a message containing them
  would be cut in half. A Buffer chunk goes through a UTF-8 decoder that holds a character split
  across chunks; `flush()` returns a last line that arrived without LF.
- `mapPiLine(line)` parses one record and returns `{ type: 'event', kind, event }`, `{ type:
'skip' }` or `{ type: 'invalid', reason }`. It never throws, and `event` is the record exactly as
  parsed, because the transcript stores the agent event unmodified and the raw line beside it.

| Pi record                                                      | Transcript `kind` |
| -------------------------------------------------------------- | ----------------- |
| `session` (the header)                                         | `system`          |
| `message_end`, message role `assistant`                        | `assistant`       |
| `message_end`, message role `assistant`, `stopReason: "error"` | `error`           |
| `message_end`, message role `toolResult`                       | `tool`            |
| `agent_settled`, `aborted: false`                              | `result`          |
| `agent_settled`, `aborted: true`                               | `error`           |
| anything else, and blank lines                                 | skipped           |

- One record carries one tool result, so the result envelope comes from `message_end`, not from
  `turn_end.toolResults`, which repeats the same messages and would double every result.
- An assistant message whose `stopReason` is `aborted` stays `assistant`: the `agent_settled`
  record that ends the run already produces the `error` envelope.
- `turn_end` is mapped to `skip` but `countTurn(record)` reports it, so a runner can enforce a
  turn cap without reading the stream twice.
- The default is skip, so a record type added by a newer Pi cannot break a run. It is not
  recorded as `invalid` either; only unusable JSON is.

Checked against a real run on 2026-11-08 (Pi 1.5.0, `opencode-go/deepseek-v4.1-flash`, in the Pi
container, one tool call; recorded as `tests/fixtures/pi/real-run.jsonl`):

- Verified: every tool result arrives as a `message_end` with `role: "toolResult"`; the run had one.
- Verified: the session header is the first record and carries `id`.
- Verified: `agent_settled` is the last record, with `aborted: false`.
- Not exercised: a batch of several tool results in one `message_end`, and an aborted run. The mapper
  still treats them as written above.
- Seen and skipped on purpose: a `message_end` with `role: "system"` (the full system prompt, about 5 KB),
  and `tool_execution_start` and `tool_execution_end`, which could later show a tool as running.

### 31. The job log shows the worker's own steps

A run's transcript held only the agent's lines, so a person watching a running job saw nothing until
the agent started, and the worktree and cleanup steps never appeared at all. `processJob` now
appends each of its steps as an `orchestrator` line: `claiming`, `base fetched`, `worktree ready`,
`merged base into branch` or `merge conflict`, `running`, `finished` or `failed`, `worktree removed`,
`slot released`. The message is a short lowercase label; the data stays small (slot, branch, base
branch, `reused`, failure `kind` and `reason`), never the environment or a secret.

- One writer per step: `createTranscriptWriter` reads the next `seq` from the file, and the steps are
  written one after another in this process, so the numbers stay in order.
- `slot acquired` comes before `claiming`, and `claiming` is what opens the run, so that step has no
  transcript folder. It goes to the process log alone.
- `failed` is written on a retried run too: the run did fail, and whether the job retries is decided
  in Postgres. A cancel that lands mid-run still wins and writes no `failed` line.
- The steps get the same known secrets as the logger (`secretsOf`), so a failure reason that quotes
  one is redacted on its way into the transcript.
- The transcript is a view, not the truth. A write that fails is logged and otherwise ignored, so a
  full disk or a bad folder can never fail or change a job.

### 32. A Linear write client behind an allow list

`src/linear-write.ts` is the first code that can write to Linear. Nothing calls it yet, so this
changes no behaviour. It has two operations:

- `moveToState(issueId, stateName)` refuses any `stateName` that is not in `allowedStatuses` before
  any network call. The caller passes the parsed `ALLOWED_STATUSES`, so the config list is the guard.
  It resolves the state id by name for `TEAM_KEY` (cached per writer), reads the issue's current
  state, and returns `'already'` with no mutation when it matches. Otherwise it runs `issueUpdate`
  and checks `success`.
- `attachPullRequest(issueId, url, title)` lists the issue's attachments and returns `'already'`
  when the url is there. Otherwise it runs `attachmentCreate` and checks `success`.

Idempotence: every write is preceded by a read, so a repeated call does not write twice.

Retry: 429 and 5xx, up to five tries, `Retry-After` honoured, otherwise `backoffDelayMs` from
`src/retry-policy.ts` (exponential, 20% jitter, capped at 60 s). This reuses the pure function
rather than copying it. `src/linear.ts` keeps its own copy of the status rule, so the copy count
is two; extract the rule on the third use.

Verified by read-only introspection on 2026-11-08 with the investing instance's key. No mutation
was run.

- Confirmed: `Mutation.issueUpdate(id: String!, input: IssueUpdateInput!)`,
  `Mutation.attachmentCreate(input: AttachmentCreateInput!)`, `IssueUpdateInput.stateId`,
  `AttachmentCreateInput.{issueId,url,title}`, `IssuePayload.success`, `AttachmentPayload.success`,
  `Query.workflowStates` with `WorkflowStateFilter.{team,name}`, `StringComparator.eq`,
  `TeamFilter.key`, `WorkflowState.id`, `Issue.state`, `Issue.attachments`,
  `AttachmentConnection.nodes`, `Attachment.url`.
- `UNVERIFIED:` the argument type of `Query.issue(id:)` (the code assumes `String!`), that `issue(id:)`
  accepts an identifier such as `CRM-19`, and any real write.
- `UNVERIFIED:` the attachment lookup reads only the first page, because the query takes no `first`.
  A ticket with more attachments than one page could miss an existing url and get a duplicate.
  Add paging before the first caller.

Open for the maintainer: the 20% jitter band, the 60 s cap, and five tries are my choices, not
taken from a measured Linear limit.

### 33. The validation policy

Phase 3 starts with its rules. `src/validation-policy.ts` decides whether an agent's work may be
pushed. It reads no file and runs no command: the caller passes in the diff. Nothing calls it yet.

- Config (`parseValidationConfig`): an ordered list of commands, at least one, names unique and
  non-blank, `run` non-blank. `timeoutSec` is optional and positive. Defaults: `maxChangedLines` 800,
  `maxRetries` 2 (0 to 5).
- Diff rules (`checkDiff`), in this order:
  - `too-large`: added and deleted lines together exceed `maxChangedLines`. Lockfiles, paths
    containing `/generated/` and `*.generated.ts` do not count.
  - `forbidden-path`: a changed path matches `forbiddenPaths` and no `allowedPaths` glob. Matches on
    add, modify and delete. A rename is checked on its new and its old path; the violation names
    the path that matched. Defaults: `.env`, `.env.*`, the same two at any depth
    (`**/.env`, `**/.env.*`, since a monorepo keeps `app/.env`), `**/*.pem`, `**/id_rsa*`,
    `.github/workflows/**`. `allowedPaths` defaults to `.env.example` and `**/.env.example`, so
    overriding `forbiddenPaths` does not drop that exception.
  - `contract-test-changed`: a `*.contract.test.ts` that is modified, deleted or renamed, on its new
    or its old path. Adding one is fine.
  - `lockfile-without-manifest`: a lockfile changed, and no `package.json` changed in the same diff.
